# Architecture

## Components

```
main/                     the application
  main.c                  boot order, the service task
  ui_nav.c                screens, the knob, taps, back gestures, idle timeout
  actions.c / vars.c      what EEZ Studio's actions.h / vars.h declare
  ui_data.c               model -> widgets, every 250 ms
  ui_climate/devices/clock/alerts/settings/setup.c   per-screen behaviour
  ui_peregrine.c          the voice screen
  ui_playbill.c           the media screen
  discovery.c             the Headwaters onboarding handshake
  bringup.c               the test jig, compiled only with no UI export
  ui/                     GENERATED by EEZ Studio

components/
  tiercel_board           the ONLY board-aware code: ST77916, CST816, knob,
                          DRV2605, backlight, LVGL port
  tiercel_audio           PDM mic capture, PCM5100A playback, levels
  tiercel_peregrine       the voice client (HTTP to Peregrine)
  tiercel_config          everything in NVS
  tiercel_model           live rig state with staleness; Playbill state
  tiercel_mqtt            the Headwaters MQTT contract
  tiercel_wifi            station + setup AP
  tiercel_portal          captive portal, validate-then-save
```

`tiercel_config`, `tiercel_model`, `tiercel_mqtt`, `tiercel_wifi`,
`tiercel_portal`, `discovery.c` and most of the UI modules are forks of
Capstan's, renamed. A fix in one product usually applies to the other.

## Data flow

```
Headwaters broker ──MQTT/TLS──▶ tiercel_mqtt ──queue──▶ service task
                                                          │ parse
                                                          ▼
                                         tiercel_model / tiercel_config (NVS)
                                                          │ getters
                                                          ▼
              LVGL task: ui_data (250 ms), ui_peregrine (40 ms), ui_playbill (50 ms)
                                                          │ text, states, flags
                                                          ▼
                                                  EEZ-generated widgets
```

- The MQTT event handler only **copies and queues**. Parsing happens on the
  service task (`main.c`, 6 KB stack, every 20 ms), never on the MQTT task.
- Retained per-device configuration has its **own queue** that never drops,
  because it arrives once per connect in the same burst as everything else.
- The model timestamps every value; a reading older than its module's
  timeout reads as `--` rather than staying on screen looking live.

## Threading

| Task | Core | Does |
|---|---|---|
| LVGL (esp_lvgl_port) | 1 | drawing, touch, knob delivery, every `lv_timer` |
| service | any | MQTT parsing, broker reconnects, services sync |
| peregrine | 0 | one utterance: listen, upload, play the reply |
| mic | 1 | PDM capture while listening |
| knob poll | esp_timer | 3 ms contact debounce |

Anything that touches LVGL from outside the LVGL task takes
`tiercel_board_lock()`. Callbacks LVGL itself runs (actions, timers, the
knob callback) already hold it and must not take it again.

## Input

The knob is delivered as a signed detent count to `ui_nav_rotate()` from an
`lv_timer`, so it always runs in the LVGL task. Taps are EEZ event handlers
calling `action_*()` in `actions.c`. The swipe and hold back gestures are read
from the touch input device on a 20 ms timer. See [screens.md](screens.md).

## Memory

- LVGL draw buffers: 2 × 24 lines in internal DMA RAM (17 KB each).
- `CONFIG_LV_USE_CLIB_MALLOC`: widgets come from the ESP heap and spill into
  PSRAM. EEZ builds every screen at boot, which overflows LVGL's own 64 KB
  pool.
- MQTT queues, the 12 s capture buffer and mbedTLS records live in PSRAM.
